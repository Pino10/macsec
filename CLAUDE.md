# Notes for AI coding assistants

MacSec is a macOS security workbench (Electron 45, electron-vite, React 18, TypeScript). It reviews code
with free scanners plus an AI reviewer, and keeps every run as a session. Read MAINTAINING.md first.

## Rules

### Exploit work (authorized only)

Exploit development is allowed in this project when it is for a system the bank owns or is contracted to test. The old blanket ban is lifted; the authorization gates are not.

Allowed:
- Exploit modules and exploit steps inside the controlled-proof engine, with an engagement record, explicit scope, caps, per-step approval, a typed confirmation, an audit record and cleanup.
- A proof of impact that is the smallest action that demonstrates the risk. Prefer a read-only proof, a callback, or a single harmless marker over a shell.
- Metasploit exploit modules in a separate `EXPLOIT_MODULES` list, never in the check/look lists. Each needs a catalogue entry, a preview, a request cap, a cleanup rule and tests.
- Adding attack tools when they are bounded, opt-in and covered by an engagement, not as default scanners.

Still not allowed:
- Any target, host or data outside the written engagement, or any third party.
- Persistence, evasion, defence disablement, destructive writes, flooding or denial of service.
- Bulk data extraction. A proof may show that data is reachable; it must not copy customer records, credentials or card data.
- Credential theft or use. Stop at the proof that credentials were returned and report it redacted.
- Automatic or hidden exploitation. Every exploit needs the engagement, the typed confirmation and the kill switch.

When a test and this policy disagree, change both deliberately in the same commit and say so in the release notes. A policy that permits something the code refuses is a bug in the policy or the code, not a licence to bypass the test.


- Security first. The window is untrusted: every IPC handler in `src/main/index.ts` validates input. Project paths must be inside the www folder or picked in a dialog (`allowedProject`). Never pass user text to a shell; use `spawn`/`execFile` with argument arrays.
- Tokens live in the Keychain (`secrets.ts`), are sent only to their own service, and are redacted from logs (`logs.ts`). Clone with a one-off auth header, never a token in the URL.
- Everything MacSec writes goes under `~/MacSec` (`paths.ts`). Scanners run with `toolEnv()` so their caches stay there. Do not write anywhere else on the Mac.
- Downloads are checked against the publisher's checksum when one exists. Releases are signed with an Ed25519 key (`build/release-signing.pub`, private half in GitHub Actions); the updater refuses an unsigned or wrongly signed release.
- Every request a guard covers connects to the address it approved (`netclient.ts`). Do not replace that with plain `fetch`. The direct web checks (`webscan.ts` exposure check, `apiscan.ts`, `webextra.ts`, `jsdeep.ts`, `recondeep.ts`, the recon probe) fetch through `guardedFetch` (`guardedfetch.ts`): guard first, then the approved address, redirects only on the same host (a test refuses a plain `fetch(` in them).
- Session credentials are never passed to a scanner tool. The signed-in crawl is `ConfirmClient` only.
- AI agents run read-only. Secrets found by scanners are never stored in findings (only the kind, file and line).
- Only test what the person owns or is allowed to test; anything not on this Mac needs their confirmation. Ordinary web and API scans only read. Keep Nuclei's `NOT_READ_ONLY` tags excluded. Never run Nmap scripts (`-sC`, `--script`), and never let WPScan guess passwords or list users.
- Control confirmations (`confirmtests.ts`) are the one exception, and only when the person turns them on for that scan. They prove a problem is real so reports have no false positives: content and parameter discovery, login and authorization checks, and WAF control tests. They must always: go through `ConfirmClient` (same host only, no redirects off the host, a request cap, a pause between requests, a stop when the server struggles); send only harmless markers, never a payload that runs code or reads other people's data; never change data (GET, plus a login form POST with a made-up user); never guess real passwords or lock a real account; confirm every finding a second time before reporting it; and keep the proof (the request, a command to repeat it, what in the answer proves it). A finding that cannot be repeated is dropped, not reported.
- Business logic checks (`bizlogic.ts`) are part of the control confirmations and follow all of their rules. They send only GETs with harmless markers (a made-up address in redirect parameters, a made-up host in `X-Forwarded-Host`) signed out (`headers: 'none'`, so a link like logout cannot sign anyone out), plus ten made-up six-digit codes to a code form with no session and no real account. Prices, coupons, races and anything else that needs a data change are never tried: they are leads that say `possible`, with no proof. Proven findings are repeated once.
- Re-test (`retest.ts`) repeats only a plain GET from a proof, signed out, without following redirects, and reports what it saw; it never marks a finding fixed. Tickets (`tickets.ts`) carry no secrets; a GitHub issue uses the Keychain token, only against `api.github.com`, only for a repository the person names.
- The live phone test (`mobilelive.ts`) is the second exception, only for an Android `.apk` and only when the person picks a test phone and confirms. It may install the app on that phone, start it, and watch it with Frida, then remove it again if MacSec installed it. It must always: use `Exec` with argument arrays and validated serials and package names (`validSerial`, `validPackage`); only observe (every Frida hook calls the original and returns its answer, no bypass scripts); send no taps, typing or intents beyond launching the app; touch only the app under test; never save a secret's value (kind, file and key name only); and download Frida's server only after its SHA-256 matches the one GitHub lists. A real phone needs the person's confirmation for that phone.
- Built-app static checks (`mobilestatic.ts`) only read the file. Its online checks are opt-in, one read-only GET per Firebase, S3 or Google Storage address found (at most six of each), no redirects, names validated, and file or key names never saved.
- Recon may use gau (`reconscan.ts`): it reads third-party archives only, never the target, and its URLs join the same in-scope list. The web scan may use wafw00f inside the firewall confirmation step (it sends a short list of probes, and it is only an identification, never an attack). App tools with a Homebrew formula (Nmap, WPScan, radare2, Ghidra, gcloud) are installed only when the person presses that row's button, with `brew` and the real environment, and the command is logged first.
- Deception (`wafdeception.ts`, with `decoys.ts`): only reads what the scan already saw, plus at most one home page and six made-up paths. A result that matches a honeypot sign is turned down to `info` with the reason and one note, never removed, never reported as a vulnerability. A scan must not try to get around a shield.
- **Tools never receive the person's session credentials.** httpx, Katana, Nuclei and WPScan run signed out; a signed-in walk is `ConfirmClient` only, capped and same-host. The header check follows a redirect only on the same host. Every guarded request connects to the address the guard approved (`netclient.ts`), never a fresh lookup.
- Ordinary web scans may optionally run ffuf content discovery (`ConfirmOptions.discover`, off by default, signed out, 20 a second, each hit proved through `ConfirmClient` and added to the pages the scan tests). The rest of the time, ordinary scans may also run `webposture.ts` (firewall and hosting hints, DNS, and the DevOps probe list), `jsdeep.ts` (the site's own scripts and their public source maps) and `cvelive.ts` (NVD, CISA and EPSS lookups). They only GET, go through `ConfirmClient` or a same-site `allowed` check, recognise a hit by what the answer contains (never the status code alone, never an HTML page for a data probe), repeat every hit once, and keep the proof. Rebuilt source stays under the session folder, and keys found in it are stored as kind, file and first four characters only. A version match is always "possible".
- A finding may say `confirmed` only with a `proof` (`risk.ts` turns it into `possible` otherwise), and `exploit` labels (Proven, Known exploited, Likely, Not proven) are worked out there, never set by hand.
- Metasploit (`msf.ts`) is the third exception, with two kinds of module and a per-module approval. Nothing runs unless the person ticked that module for that scan (`approved`, validated against `catalog()`). "Check" modules (a fixed allowlist, `MODULES`) get only `use <module>; set RHOSTS; set RPORT; check; exit -y`. "Look" modules (`LOOK`: auxiliary/scanner banner, version, title, methods and certificate scanners only) get only `use <module>; set RHOSTS; set RPORT; set THREADS 1; run; exit -y`. Both go through `execFile` with an argument array and validated host and port. Check and look lists stay non-exploit. Exploit modules belong to a separate list and to the controlled proof: they may be added there with an engagement, a catalogue entry, a preview, a cap, cleanup and tests. Logins, brute force, dumps, floods, payloads and listeners stay out of the check/look lists. It is never installed by MacSec and only runs against hosts the person owns or that are local. A check hit needs the module's own "vulnerable" answer and keeps the command as proof; "appears" and "unsupported" are never `confirmed`; a look result is an observation (`info`), and an advertised risky method is only `possible`.
- Other attack tools (Hydra, drozer, Dalfox, hashcat, Pacu and the rest in `optional.ts`) may be integrated when they are bounded, opt-in and run inside an authorized engagement. They stay off by default, never run automatically, and are still listed when not integrated. ffuf, sqlmap and wafw00f are bounded tools covered by their own rules below.
- Controlled proofs (`src/main/impact/`, `engagement.ts`) are the fourth and last exception, and the strictest. This is the only part of MacSec that can change data or read real data, so a rule here is not a preference: it is the reason the feature is allowed to exist.
  - **No engagement, no run.** `engagementProblem()` must return null before the first request: live, not revoked, inside its window, host covered, goal allowed, caps not used up. Caps are counted from the runs stored in `~/MacSec/impact-runs`, never from a number the window sends.
  - **The phrase is typed, not defaulted.** `runProblem()` must pass with the exact `EXPLOIT <host>`, the ticked step ids, and the leftover acknowledgement for any write step. A write step also needs `integrity` in the engagement and an undo sentence.
  - **Every step is a bound.** A catalogue entry (`catalog.ts`) says what it sends, what it never does, its request cap and its cleanup, and `actions.ts` must not exceed that cap. Adding a proof means adding a catalogue entry, a runner, a preview and tests before it can be used.
  - **Only the target, only through the client.** Every request goes through `ImpactClient` (it always has a network guard, its own when none is passed, and connects to the address the guard approved via `netclient.ts`, never a fresh lookup; only a test may turn the guard off or inject a fetch; host covered by the engagement, same origin except a verification GET with no credentials, private addresses only when the engagement says staging, metadata addresses never, manual redirects, a delay, a stop when the server struggles, and the kill switch).
  - **Stop at the first proof.** A campaign ends when each goal class is proven, when the caps or the clock run out, or after three failing steps. Never keep going to collect more damage.
  - **Discovery with ffuf (`content-discovery`)** sends hundreds of GETs, so it is bounded like nothing else: signed out (no cookie, no token), never `-r` (no redirects), at most 20 requests a second, the list capped and validated in `wordlistfiles.ts` (plain paths only, no `..`), and `client.reserve()` must count the whole list against the engagement *before* ffuf starts. Every path it reports is asked again through `ImpactClient` and compared with a path that cannot exist. The optional web-scan discovery step follows the same limits and proves each hit through `ConfirmClient`.
  - **The anonymous read (`auth-bypass`)** sends no cookie and no token, ever, and its `expect` string is the person's own; the runner refuses to run when it is empty. A hit must repeat on a second anonymous request.
  - **sqlmap (`sql-injection-proof`) is fingerprint only.** Exactly one parameter (`-p`), GET only, `--risk=1 --level=1 --technique=BE --threads=1 --timeout=15 --retries=0 --smart`, never `--dump`, `--sql-shell`, `--os-shell`, `--file-read`, `--file-write`, `--tamper`, `--forms` or credential testing. It calls `client.reserve(80)` before it starts, deletes its own session folder afterwards, and a finding may only come from sqlmap naming the parameter and the technique. It never runs outside an engagement.
  - **No flooding, no bulk dumps, no persistence, no evasion.** Exploit steps are allowed inside the engagement; denial of service is not. The availability proof is five sequential requests at the very most and stops on the first 429 or 503. A write is one plain text file with a random name, deleted again or listed as a leftover with its exact address. A shell or session is allowed only when the engagement explicitly names it, is capped, and is closed and cleaned up in the same run; a callback is the safer proof. Nothing guesses passwords, dumps customer data, or hides from a firewall.
  - **A chain is evidence, not a story.** `chainsOf` may show a path only when every part was found as a separate finding, and every path must carry `breakAt`: the one cheapest fix that removes it. Never claim a chain was exploited, and never build one from a ruled-out or triaged finding.
  - **The record is part of the proof.** The audit log keeps the method, the masked address, the status and a hash, never a cookie or a body value; `maskUrl` and `maskSecrets` are the only ways a value may appear. A run without a stored record is a bug.
  - **The planner cannot invent anything.** `planFromRules` is the default and uses no AI. The optional AI planner sees findings only (never code), is called once, and its answer is passed through `checkStep()`; anything not on the catalogue or not on the target origin is dropped with a note. Do not relax that.
  - Metasploit exploit modules are not on the check list in `msf.ts` (several execute code during `check`). A real exploit belongs to the controlled proof `msf-run` and to an explicit `EXPLOIT_MODULES` list. Each run needs the engagement, the typed confirmation, a cap, cleanup and a proof: prefer a callback command that MacSec writes (a curl or wget to a listener on this Mac); a session or meterpreter is allowed only when the engagement names it, and it must be closed and removed in the same run. A run with no proof is `not-proven`. Do not add a module known to crash a host or write a file MacSec cannot remove.
- Protocol checks (`oauth.ts`, `jwt.ts`, `graphql.ts`, `sessioncheck.ts`) follow the control confirmation rules and use GET, plus one kind of POST: a GraphQL query (never a mutation or subscription: `ConfirmClient.query` refuses those words). They read sign-in links and the provider's own settings, send made-up callback addresses and origins that end in `.invalid` (nothing can receive them), never contact a provider that is not on the site being tested, never sign in, never guess passwords or codes and never send deep, wide, aliased or long-batch GraphQL queries. The person's own token may be sent back with its signature removed or `alg: none`, claims unchanged, GET only, and only to a page that already answers differently with and without the token. Token, session id and secret values are never written to a finding, proof, title or log (kind, name, length and fingerprint only: test for it). Forms are never submitted: CSRF is a lead (`possible`, no proof).
- Autopilot (`autopilot.ts`): the AI only picks from the fixed `MENU` and MacSec validates every action (`allowed`: on the menu, same site, not a logout or delete page, not repeated, three rounds, six per round, fourteen in all). The AI sends no request, writes no finding and chooses no payload. Page text it reads is untrusted, shortened, stripped of control characters and inside a data block. Do not add a menu action that sends free-form requests or bodies.
- Injection checks (`injection.ts`) use only GET with harmless markers (a made-up tag, a math expression, one quote versus two, a line-break marker), recognise a hit by what the page contains, repeat every hit once, and keep the proof. POST forms are listed as leads and never submitted.
- White box (`routemap.ts`) only reads the code folder the person picked (inside www or chosen in a dialog). Private routes found there are tried signed out with one GET each; a hidden route is a lead unless the answer proves it.
- The checklist walk (`checklist.ts`) marks an item found or clear only from what a scan step did. The AI may mark an item only with the ids of existing findings or "profile"; anything else stays manual. Nothing is invented.
- Service probes (`servicedeep.ts`) send only read-only questions (PING, banner, version) on ports already found open, and recognise a hit by the answer, never by the port alone.
- This Mac checks (`machecks2.ts`) only read. Secrets found in files or shell history are reported as kind, file and line, never the value.
- Deep recon (`recondeep.ts`) only reads: headers, TLS, DNS and the DevOps probe list, through the shared clients.
- More mobile checks (`mobiledeep.ts`) and the MASVS checklist (`masvs.ts`) only read the files of an app and the findings of a session. They never run the app or send a request. A MASVS control reads "Clear" only when the step that can see it ran and no finding belongs to it; a control that needs a person never reads "Clear".
- Decoys and ignore memory (`decoys.ts`, `ignored.ts`): they only read what a scan already saw and never send a request. A decoy is turned down to `info` with the reason and is never removed from the report. Only your own choice (`ignored.json` in `~/MacSec/config`) marks a finding "Not a problem" on later scans, and a rule holds the finding id or title and place, never a secret value. Keys are shown as the first four characters and the length only.
- MobSF (`mobsf.ts`) listens on 127.0.0.1 only, starts from a validated folder or Docker with argument arrays, never stops a MobSF it did not start, and opens only in its own sandboxed window that may show nothing but MobSF on this Mac.
- Every AI agent run (`claude -p ... --permission-mode plan`) also passes `--strict-mcp-config`, so it never loads the person's own MCP servers (a test checks this).
- Network guard (`netguard.ts`), correlation (`correlate.ts`), verification states (`shared/verification.ts`) and the accuracy score (`benchmark.ts`) only read. The guard sits in `ConfirmClient`: it refuses cloud metadata addresses, a name that mixes public and private answers, and a name that moves from public to private during a scan. It never contacts the target itself. `correlate` merges only findings of the same kind at the same place from different tools, never two findings that both carry proof, and never drops a proof. Verification is worked out from the finding, never set by hand, and `confirmed` still needs a proof. ASVS is chapter level only, so no requirement number is guessed.
- DKIM and DNSSEC checks (`webposture.ts`) only read DNS. DKIM asks for a fixed list of common selectors (`DKIM_SELECTORS`) and reports a weak, withdrawn or test-mode key only with the record as proof; not finding a selector says nothing. DNSSEC asks one DNS over HTTPS service (Cloudflare) for the domain's DS record, name only, and reports "not signed" only after a clean empty answer, as `possible`. Tests inject the resolver and the DoH function, so they never touch the network.
- Traffic check (`traffic.ts`, `trafficcapture.ts`) only reads a HAR and only listens: MacSec never touches the phone or emulator (no adb, no proxy setting, no certificate install: the person does that). mitmdump runs with an argument array, listens only on 127.0.0.1 or one of this Mac's own local network addresses (`validListen`), keeps `block_global=true`, and only needs the person to confirm the app is theirs to test. The HAR can hold tokens, so it is deleted right after it is read and never copied into a session; findings keep only the request line cut at the `?`, header and field names, never values (a test checks it). Only a request that was seen is reported, so findings carry a proof and there is no `possible`; an empty capture is an `info` note and never proves pinning. mitmproxy is installed by the toolbox (uv) like the other Python tools.
- Headless (`cli.ts`, `--headless` in `index.ts`): it creates no window, no tray and no IPC, and it must exit with the documented codes (0 clean, 1 threshold, 2 error, 3 scanners missing). A baseline may only skip findings the team accepted with `checkId|place`; it must never hide a finding from the session or the report, and `--no-baseline` must always work. `--json` stays one object on stdout, with progress lines on stderr or as plain text before it.
- Storage (`storage.ts`): deleting sessions needs an explicit click and a stated age, never a background sweep, and it reports how many it removed. Search and storage only read until the person deletes.
- The safety page (`pages/Safety.tsx`) is the plain-English copy of these rules for security teams. When a rule here changes, change the page too, in the same commit. It must say that controlled proofs exist and when they may run, never claim a certification or compliance, and show an organisation name only when the person typed it.
- UI and docs: plain, friendly English for non-experts. Never use em dashes; use a colon and a space instead.

```sh
npm run typecheck

```
